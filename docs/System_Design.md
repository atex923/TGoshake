## 1. 使用流程總覽

```text
首次啟動／權限說明
        ↓
首頁／歷史行程
        ↓
新增記錄設定
        ↓
裝置固定與 5 秒靜止檢查
        ↓
即時記錄 ── 暫停／繼續 ── 畫面或藍牙控制器手動標記事件
        ↓
停止確認
        ↓
資料封存與事後分析
        ↓
結果地圖 ↔ 熱點詳情 ↔ 三軸波形
        ↓
匯出 CSV／JSON 或返回歷史行程
```

### P04 權限與裝置檢查

| 檢查 | 成功條件 | 失敗處理 |
|---|---|---|
| Motion 可用性 | `isDeviceMotionAvailable == true` | 無法開始記錄，說明此裝置不支援 |
| 定位服務 | 系統定位開啟 | 提供設定引導；允許使用者只做無 GPS 測試記錄，但明確標記 |
| App 定位權限 | While In Use | 顯示系統權限要求與用途文案 |
| 精確位置 | Full Accuracy | Reduced Accuracy 仍可記錄，但地圖顯示「位置精度受限」 |
| 可用空間 | 預估至少可記錄 60 分鐘 | 空間不足時阻止長時間開始並提示清理 |
| 電量 | 顯示目前電量 | 低於 20% 顯示警告，不強制阻止 |

### P05 固定方式與靜止檢查

固定圖示與文字必須明確：

- iPhone 平放，螢幕朝上。
- 手機頂端朝列車行進方向。
- x 軸視為橫向、y 軸視為縱向、z 軸視為垂直方向。
- 使用防滑墊或穩固支架；不可手持、放在鬆軟包包內或讓手機在桌上滑動。
- 記錄途中若拿起手機，按「暫停」後再移動。

按「開始 5 秒檢查」後顯示倒數、姿態穩定度與背景雜訊。檢查結果分為：

- 通過：姿態與基線穩定，可開始。
- 可記錄但有警告：輕微傾斜或背景振動偏高。
- 未通過：持續移動、裝置翻面或資料中斷；重新檢查。

開始時保存基線統計，不直接從之後訊號中扣掉所有差異，避免消除真實低頻振動。

#### 藍牙控制器設定

固定方式確認頁增加「藍牙標記控制器」卡片：

| 狀態／操作 | 行為 |
|---|---|
| 尚未設定 | 顯示「連接控制器」與「略過」；藍牙不是開始記錄的必要條件 |
| 搜尋中 | 顯示附近相容裝置，不自動連接未知裝置 |
| 已連接 | 顯示裝置名稱、連接方式、電量（若裝置提供）及指定按鍵 |
| 按鍵測試 | 使用者按一下控制器，畫面立即顯示收到的按鍵、時間與回饋 |
| 測試失敗 | 顯示排解說明，仍可改用畫面「標記事件」按鈕 |

第一版定義兩種相容途徑：

1. 支援 Apple Game Controller profile 的藍牙控制器，透過 GameController framework 接收按下與放開事件。
2. 經測試的自訂 BLE 按鍵，透過 CoreBluetooth 連線至已知 service／characteristic UUID。

常見藍牙自拍器多半模擬音量鍵或鍵盤按鍵，其行為因型號而異；未完成實機相容測試前，不宣稱所有自拍器都能使用，也不以攔截系統音量鍵作正式方案。

- 第一次按「結束記錄」只顯示確認，不立即銷毀感測器工作階段。

## 3. 執行邏輯與狀態機

### 狀態定義

```text
idle
  └─> preflight
       ├─> permissionBlocked
       └─> calibrating
            ├─> calibrationFailed
            └─> recording
                 ├─> paused ──> recording
                 ├─> interrupted
                 └─> stopping
                      └─> sealing
                           ├─> processing
                           │    ├─> complete
                           │    └─> analysisFailed
                           └─> storageFailed
```

| 狀態 | 允許操作 | 寫入行為 |
|---|---|---|
| `idle` | 建立或選擇行程 | 不開啟資料檔 |
| `preflight` | 權限、空間、感測器檢查 | 建立暫存 session manifest |
| `calibrating` | 取消、重新檢查 | 暫存 5 秒資料；不混入正式行程 |
| `recording` | 暫停、標記、停止 | Motion 與 GPS 持續串流寫入 |
| `paused` | 繼續、停止 | 停止 Motion；寫入 pause gap，不把兩段時間接起來 |
| `interrupted` | 返回後繼續或結束 | 保存中斷起訖及原因 |
| `stopping` | 等待 | 禁止新 UI 命令；停止資料來源 |
| `sealing` | 等待 | 排空 buffer、關檔、寫 checksum 與完成狀態 |
| `processing` | 可離開頁面 | 讀取已封存來源檔，建立分析檔 |
| `complete` | 檢視、匯出、重算 | 來源檔唯讀 |
| `analysisFailed` | 重試分析、匯出來源檔 | 不刪除行程 |

### 開始記錄順序

1. 驗證欄位、Motion、定位、磁碟空間及電量。
2. 建立 session UUID 及 temporary package。
3. 寫入 `manifest.json`，狀態設為 `preflight`。
4. 執行 5 秒靜止檢查並保存基線摘要。
5. 捕捉時間錨點：UTC wall-clock 加 `systemUptime`。
6. 先開啟檔案 writer，再啟動 Motion，最後啟動 Location。
7. 狀態改為 `recording`，開始節流後的 UI 更新。

### 結束記錄順序

1. 接受停止命令並把狀態改為 `stopping`。
2. 停止 Motion 和 Location 新事件。
3. 排空所有 buffer，補寫最後的品質統計。
4. 關閉檔案並計算大小與 checksum。
5. 將 temporary package 原子改名為正式 session package。
6. 狀態改為 `processing`，執行事後分析。
7. 分析成功寫入 `events.json` 與摘要；失敗則保留來源檔供重試。

## 4. 感測與時間同步

### Motion 資料

主要使用 `CMDeviceMotion`，每筆保留：

- `timestamp`（自裝置開機後的單調時間）
- `userAcceleration.x/y/z`
- `gravity.x/y/z`
- `rotationRate.x/y/z`
- attitude quaternion；CSV 可另輸出 roll、pitch、yaw 方便閱讀
- 資料品質旗標

要求更新間隔 0.01 秒，但所有運算以實際 timestamp 為準。若硬體只提供較低頻率，App 照實保存並顯示，不自行複製樣本湊成 100 Hz。

### Location 資料

每筆保存：

- timestamp、latitude、longitude、altitude
- horizontalAccuracy、verticalAccuracy
- speed、speedAccuracy
- course、courseAccuracy
- precise／reduced accuracy 狀態

負的 accuracy、speed 或 course 依 Apple API 語意標為無效，不改寫成 0。

### 共用時間軸

Core Motion 使用單調時間，Location 使用日期時間。開始時保存：

```text
anchorUTC = Date()
anchorUptime = ProcessInfo.processInfo.systemUptime
motionUTC = anchorUTC + (motionTimestamp - anchorUptime)
```

主要分析一律使用單調 `elapsed_s`，UTC 只負責和 GPS／匯出對齊。若使用者或系統在途中更改時鐘，不可讓 Motion 時序倒退。

## 5. 藍牙控制器主觀感受標記

### 設計目的

藍牙控制器讓使用者在不拿起 iPhone 的情況下，標記「我主觀感覺這裡晃動較大」。它是人工標註資料，不是感測器自動判定，也不直接等於軌道異常。

### 按鍵模式

| 操作 | 建立的標記 | 初始區間 |
|---|---|---|
| 單按 | 主觀劇烈晃動事件 | 按下時間前 3 秒至後 5 秒 |
| 按住 | 主觀晃動區間 | 按下前 1 秒至放開後 1 秒 |
| 連按兩次 | 加強感受標記 | 仍只建立一筆事件，`perceivedIntensity = veryHigh` |
| 長按第二指定鍵 | 取消最近標記 | 只可取消最近 10 秒內尚未封存的人工標記，並留下取消紀錄 |

單按前後時間、雙按間隔及取消窗口都是版本化參數。預設涵蓋按下前 3 秒，是為了容納使用者感受到晃動後才反應的時間；此區間只作回看範圍，不代表精準的事件起訖。

### 輸入處理邏輯

1. 控制器回呼到達時立刻讀取 `systemUptime`，不可等 UI 動畫結束才計時。
2. 以按鍵 down／up 建立狀態，執行約 80–120 ms debounce，避免接點彈跳造成重複事件。
3. 單按先建立 pending marker；等雙按判定窗口結束後再封存為單按或雙按。
4. 按住超過設定門檻後切換為 interval 模式，放開時結束區間。
5. 將控制器事件轉到和 Motion 相同的單調時間軸，再配置 GPS。
6. App 以短震動和畫面閃示確認已收到按鍵；不得因沒有控制器震動馬達而漏記。
7. 控制器斷線、重新連線、按鍵重複或未知指令都寫入品質日誌。

### 人工標記資料

`markers.json` 每筆至少保存：

```text
id, sessionID, source
buttonDownElapsed_s, buttonUpElapsed_s
reviewStartElapsed_s, reviewEndElapsed_s
receivedUTC, inputMode, perceivedIntensity
controllerIDHash, controllerName, transport
buttonCode, debounceApplied, connectionState
latitude, longitude, horizontalAccuracy_m, locationStatus
note, isCancelled, cancelledAtElapsed_s
```

- `source` 可為 `onScreen`、`gameController` 或 `customBLE`。
- `controllerIDHash` 只用於辨識同一控制器，不保存可跨 App 追蹤的原始硬體識別值。
- 人工標記與 `events.json` 的自動振動事件保持不同 ID 與來源；分析時可計算兩者重疊率，但不互相覆寫。

### 延遲與誤差

| 來源 | 影響 | 處理方式 |
|---|---|---|
| 人的反應時間 | 通常晚於實際開始晃動，且每人不同 | 單按預設向前涵蓋 3 秒；保存按下原始時間 |
| 藍牙傳輸延遲 | 按鍵到 App 的時間不是零 | 保存 App 收到事件的單調時間；按鍵測試量測穩定性但不假裝得知真實發射時間 |
| debounce／雙按等待 | UI 確認可能稍晚 | 原始 down 時間先保存，等待只影響分類，不改變時間戳 |
| GPS 更新延遲 | 按鍵當下不一定有新座標 | 依前後有效 GPS 插值並保留 accuracy |
| 控制器斷線 | 使用者以為已標記但 App 未收到 | 顯示醒目斷線狀態；畫面按鈕永遠可用 |
| 誤觸 | 產生錯誤人工事件 | 10 秒內可用第二鍵取消；保留取消稽核紀錄 |

### 安全與隱私

- 控制器只作 App 內事件標記，不控制列車、不傳送資料至外部服務。
- 配對及按鍵設定只能在非記錄中進行，避免行程中分散注意力。
- 裝置名稱可能含個人自訂文字；匯出時預設使用雜湊 ID，可選擇移除名稱。
- V0.0.1 只保證 App 在前景記錄時接收按鍵，不宣稱背景或鎖屏下可靠。

## 6. 三軸方向與姿態處理

### 固定方向

手機直向平放、螢幕朝上、頂端朝行進方向時：

| iPhone 軸 | TGoshake 定義 | 正方向 |
|---|---|---|
| x | 橫向 | 朝手機右側 |
| y | 縱向 | 朝手機頂端／列車前方 |
| z | 垂直 | 離開螢幕向上 |

### 姿態補償原則

- `userAcceleration` 已由 Core Motion 分離重力，但仍位於手機座標。
- 保留手機座標來源值，另以 attitude quaternion 建立分析座標。
- 垂直軸依重力方向校正；水平面依開始時手機頂端方向定義縱向與橫向。
- 不依賴磁北決定列車方向，因車廂鋼材與電氣設備可能干擾磁力計。
- 手機若相對固定座突然轉動或傾斜，標記 `mountMovementSuspected`，不盲目把該段修正成正常振動。

## 7. 偵測方式

V0.0.1 同時處理「自動振動事件」、「使用者主觀感受標記」及「量測品質事件」。三者必須分開，避免把手機滑動或人工按鍵誤認為演算法判定的軌道熱點。

### 振動事件特徵

將有效資料切成 1 秒窗、50% 重疊，每窗計算：

| 特徵 | 用途 |
|---|---|
| 縱向、橫向、垂直 RMS | 表示該方向持續振動能量 |
| 三軸合成 RMS | 表示整體振動強度 |
| 最大絕對值 | 找單次明顯衝擊 |
| Peak-to-peak | 表示窗內完整擺幅 |
| 95 百分位數 | 降低單一極端點對結果的支配 |
| Jerk RMS | 找快速變化與突發衝擊 |
| Rotation-rate RMS／峰值 | 找搖擺及 roll 動態 |
| 有效樣本率與缺樣率 | 決定這個窗是否可評分 |

### 初始事件分數

各特徵先以該趟有效資料的 median 與 MAD 做 robust normalization，再產生候選分數：

```text
scoreRaw =
    0.40 × zMAD(verticalRMS)
  + 0.25 × zMAD(lateralRMS)
  + 0.20 × zMAD(resultantP95)
  + 0.10 × zMAD(jerkRMS)
  + 0.05 × zMAD(rotationRateRMS)
```

權重是 V0.0.1 實驗起點，寫入 `analysisVersion`，需經實車資料驗證後才能凍結。若某窗有掉樣、定位不確定或疑似手機移動，分數仍可計算但必須帶品質標記。

### 相對級別

| 級別 | 本趟有效窗百分位 | 地圖顏色 | 意義 |
|---|---:|---|---|
| 平穩 | 0–50% | 綠 | 相對於本趟較低 |
| 注意 | 50–80% | 黃 | 中等變化 |
| 明顯 | 80–95% | 橘 | 相對劇烈，值得回看 |
| 劇烈 | 95–100% | 紅 | 本趟最高的一組，不代表危險 |

連續高分窗或空間距離相近的橘／紅窗合併為事件群。合併時保存原始窗清單，不只留下最大值。

### 量測品質事件

| 事件 | 初步判定方式 | 處理 |
|---|---|---|
| Motion 掉樣 | 實際間隔大於近期中位間隔的 2.5 倍 | 切段、標記 gap，不跨缺口濾波 |
| 取樣率下降 | 5 秒窗中位頻率低於本次裝置穩定基線的 80% | 顯示黃燈並保存「要求值、基線值、實際值」；不因硬體上限低於要求值而持續誤報 |
| 手機疑似被移動 | attitude 突變加 rotation peak，且不符合一般車體連續性 | 標記，不自動刪除 |
| 感測飽和／clipping | 多個連續樣本貼近同一極值 | 標記該窗低可信度 |
| GPS 無效 | horizontalAccuracy < 0 或時間過舊 | 不配置地圖位置 |
| GPS 精度差 | horizontalAccuracy 超過初始門檻 50 m | 顯示灰色／低可信度，可調參數但需版本化 |
| GPS 跳點 | 相鄰點推算速度不合理，且超過精度範圍可解釋程度 | 保留來源點但不畫入有效軌跡 |
| 時鐘異常 | UTC 倒退或與單調時間偏差突變 | 以單調時間為主並寫入警告 |

### 主觀標記與自動事件比對

- 人工標記以紫色手形 Annotation 顯示，自動事件仍使用綠／黃／橘／紅。
- 若人工標記區間與自動橘／紅事件重疊，顯示「感受與感測皆明顯」。
- 若只有人工標記，顯示「使用者感受明顯，感測分數未達本趟高百分位」。
- 若只有自動事件，顯示「感測變化明顯，未收到人工標記」。
- 計算 time overlap、最近事件時間差及空間距離，但不得把重疊率包裝成安全準確率。

## 8. 雜訊與濾波規劃

### 原則

1. 來源資料永遠保留，不覆寫、不先平滑後才存檔。
2. 濾波只產生分析通道，所有參數寫入 metadata。
3. 真實鐵路衝擊可能看起來像尖峰，不能用一般 outlier removal 直接刪除。
4. 品質可疑的資料以旗標隔離，而不是偷偷修正。

### 即時顯示通道

| 步驟 | 規劃 |
|---|---|
| 重力分離 | 使用 `CMDeviceMotion.userAcceleration` |
| 姿態處理 | 投影至列車縱／橫／垂直分析座標 |
| 高通 | 2 階 Butterworth，約 0.5 Hz，減少非常緩慢的姿態漂移 |
| 低通 | 2 階 Butterworth，約 30 Hz，降低接近 Nyquist 的高頻雜訊 |
| 圖面降採樣 | 每 5–10 個樣本取 min／max envelope 或分桶摘要，不能只取每第 N 點而漏掉峰值 |

即時通道採 causal filter，因此會有相位延遲，只用於現場顯示和暫定強度。

### 事後分析通道

| 步驟 | 規劃 |
|---|---|
| 時間檢查 | 排序、去除完全重複 timestamp、依 gap 切段 |
| 重採樣 | 只在短小缺口內插值到固定頻率；過長缺口保持分段 |
| 頻帶 | 初始研究頻帶 0.5–30 Hz |
| 濾波器 | 4 階 Butterworth band-pass，以 forward/backward 方式取得近似零相位結果 |
| 邊界 | 每段兩端標記 filter transient，不把邊界樣本列為高可信度事件 |
| 特徵 | 對濾波後通道算 RMS、P95、peak、jerk、rotation rate；來源值另供回看 |

100 Hz 的 Nyquist 頻率只有 50 Hz，因此無法完整涵蓋 ISO 2631 文獻常見的最高 80 Hz 分析範圍。V0.0.1 的 0.5–30 Hz 是熱點篩查頻帶，不得標示為完整 ISO 2631 計算。

### 不採用的自動清理

- 不對加速度套移動平均後覆寫來源檔。
- 不以「超過三倍標準差」直接刪除衝擊。
- 不在 GPS 中斷時把最後座標複製到後續所有事件。
- 不把暫停前後資料接成連續時間序列。
- 不用不同手機型號的未校正數值建立共同絕對門檻。

## 9. 分析方式

### 單趟分析

1. 檢查 session 完整性、schema、checksum 與資料欄位。
2. 建立 Motion 單調時間軸及 GPS UTC 時間軸。
3. 執行姿態處理、分段、短缺口重採樣及分析濾波。
4. 計算 1 秒／50% overlap 特徵。
5. 排除完全無效窗；品質可疑窗保留但不納入基線統計。
6. 以有效窗 median／MAD 建立相對分數及 percentile。
7. Motion 時間對齊 GPS；產生位置可信度。
8. 合併相鄰橘／紅事件，建立地圖 overlay。
9. 寫入 `events.json`、摘要與 `analysisVersion`。

### GPS 配置方式

對每個 Motion 窗中心時間：

- 找出時間前後兩筆有效 Location。
- 只有兩點間隔不超過初始門檻 10 秒，且精度可接受時才做線性時間插值。
- 圓圈半徑至少使用該位置的 horizontalAccuracy；不以小圓假裝精準。
- 只有單側位置、時間差太大或位於隧道時，事件保留但列為 `locationUncertain`。
- V0.0.1 不把點吸附到推測的鐵道路線。

### 跨趟分析的保留接口

V0.0.1 不在 UI 合併行程，但資料模型須保留下列分組鍵：

```text
routeName + direction + trainType + carNumber/mountPosition
+ deviceModel + speedBand + analysisVersion
```

後續只在條件相近時比較同一空間區段的 median、MAD、事件重現率與趨勢。

## 10. 誤差來源與控制

| 誤差／雜訊來源 | 可能影響 | V0.0.1 控制方式 | 尚存限制 |
|---|---|---|---|
| 手機 MEMS 偏差與機型差異 | 相同振動得到不同振幅或頻率反應 | 保存機型、OS、基線及實際取樣率 | 未經外部校正，不可建立跨機型絕對標準 |
| 固定座、桌板、座椅共振 | 放大或衰減特定頻率 | 固定方式必填、相同方式重複測試 | 仍量到車廂及固定介面的綜合反應 |
| 手機角度錯誤 | 三軸串擾 | 固定教學、5 秒姿態檢查、重力與 quaternion 輔助 | 手機在行程中滑動仍可能失真 |
| 使用者觸碰手機 | 產生巨大假事件 | 暫停移動、手動「手機被碰觸」標記、姿態突變偵測 | 自動分類不可能百分之百準確 |
| 車型、轉向架、懸吊 | 改變車體振動 | 保存車種、車次、車廂；條件分組 | 無車輛工程資料時不能反推出單一軌道原因 |
| 車速 | 相同軌道在不同速度下振動不同 | 保存 speed／accuracy，後續使用速度帶 | GPS speed 本身也有誤差 |
| 彎道、道岔、橋梁、煞車 | 正常結構或操作也可能形成高峰 | 手動標記、地圖與波形聯看 | 沒有官方基礎設施資料時只能描述現象 |
| 取樣抖動與掉樣 | 頻域及 jerk 特徵失真 | 使用 timestamp、短缺口有限插值、長缺口切段 | 嚴重掉樣的窗只能降級或排除 |
| GPS 多路徑、遮蔽 | 熱點位置偏移或跳點 | 保存 accuracy、跳點檢查、圓圈表示誤差 | 車廂內及高樓／山區仍可能有數十公尺誤差 |
| 隧道無 GPS | 無法直接定位熱點 | 保留未定位事件，不假造座標 | V0.0.1 無完整慣性定位或 map matching |
| 時鐘變更 | Motion 與 GPS 錯位 | 主要使用單調時間，UTC 僅對齊 | 系統暫停造成的長 gap 仍需標記 |
| 電量與熱節流 | 更新率下降或系統中止 | 顯示電量、實際頻率與資料品質 | 前景長時間記錄仍耗電 |
| 數位濾波 | 相位延遲、邊界假象、峰值改變 | 即時與事後通道分開、來源資料不變、邊界標記 | 濾波參數仍需實車與參考儀器驗證 |
| 人工按鍵反應時間 | 標記晚於使用者開始感到晃動 | 保留原始按下時間並向前提供 3 秒回看窗 | 個人反應差異無法完全校正 |
| 藍牙延遲或斷線 | 標記時間偏移或事件未送達 | 單調到達時間、連線狀態、按鍵測試及畫面備援 | 無控制器端時鐘時不能精確分離傳輸延遲 |

## 11. 紀錄與防損毀方式

### Session package

```text
<session-uuid>.tgoshake/
  manifest.json
  metadata.json
  motion.csv
  location.csv
  markers.json
  events.json
  checksums.json
```

| 檔案 | 寫入時機 | 說明 |
|---|---|---|
| `manifest.json` | 全程 | session 狀態、schema、檔名及復原資訊 |
| `metadata.json` | 開始及結束 | 裝置、行程、固定、基線、權限與版本 |
| `motion.csv` | 記錄中串流 | 高頻 `CMDeviceMotion` 來源資料及分析座標 |
| `location.csv` | 收到更新時串流 | 完整 Location 與精度欄位 |
| `markers.json` | 畫面或藍牙控制器標記時 | 按下／放開／回看區間、來源、控制器狀態、GPS 與文字 |
| `events.json` | 事後分析 | 視窗特徵、事件群、地圖位置與品質 |
| `checksums.json` | 封存時 | 各來源檔大小與 SHA-256 |

### 寫入策略

- Motion callback 只做必要轉換並送入固定容量 buffer，不在 callback 做地圖或重分析。
- Writer 使用單一 serial queue，累積約 100 筆或 1 秒即寫入。
- 定期更新 manifest 的最後安全 offset；App 崩潰後只截斷不完整的最後一列。
- 使用 temporary package 記錄，正常封存後原子改名。
- UI、寫檔、分析採不同工作單元；分析永遠讀已封存檔案。
- 來源檔封存後視為唯讀；重新分析只替換衍生資料和版本化摘要。

### 容量估算

100 Hz、每筆包含完整 Device Motion 及文字 CSV 時，保守預估每小時約 50–100 MB，實際值由小數位數與欄位數決定。開始前以剩餘空間估算可記錄時間；實作階段需用真實輸出量測，不用理論值宣稱容量。

## 12. 圖面與地圖整合方式

### 地圖圖層

由下而上：

1. Apple MapKit 底圖。
2. 有效 GPS 軌跡細灰線，保留實際量測路徑。
3. 依分析窗級別切分的彩色 `MapPolyline`。
4. 橘／紅事件群 `MapCircle`；圓半徑主要表示位置不確定性，顏色表示振動級別。
5. 手動標記 `Annotation`。
6. 選中事件的高亮外框與資訊卡。

### 顏色語意

| 顏色 | 振動語意 | 不代表 |
|---|---|---|
| 綠 | 本趟較平穩 | 軌道一定正常 |
| 黃 | 中等變化 | 需要維修 |
| 橘 | 本趟相對明顯 | 已確認異常 |
| 紅 | 本趟最高百分位 | 危險或故障 |
| 灰 | 定位或資料品質不足 | 沒有振動 |
| 紫 | 使用者主觀感受標記 | 演算法已確認異常 |

### 地圖與波形聯動

- 點選彩色軌跡或圓圈，設定 `selectedEventID`。
- 下方詳情卡顯示該事件，波形游標跳到事件中心時間。
- 拖動波形游標時，地圖高亮最接近該時間的有效位置。
- 改變事件篩選時，只改變 overlay 顯示，不重算或覆寫分析結果。
- 過多視窗不逐窗建立 overlay；先合併同色相鄰線段，橘／紅才顯示圓圈，以維持地圖效能。
- 圓圈半徑不直接表示振動強度，避免與 GPS 誤差語意混淆；強度用顏色、外框與詳情數值表達。
- 藍牙與畫面人工標記使用相同紫色手形，但詳情卡顯示來源；按住建立的區間以紫色半透明帶呈現。

## 14. 驗證項目

### 單元測試

- 時間錨點轉換、UTC 改變時仍維持單調順序。
- 1 秒窗與 50% overlap 邊界正確。
- gap 不會被濾波或事件合併跨越。
- Butterworth 濾波對已知合成正弦波的增益與頻帶合理。
- median／MAD 在 MAD 為 0 時不除以 0。
- GPS 無效值、跳點、插值門檻與精度半徑處理。
- 相同來源檔重算得到相同 events 與 checksum。
- 暫停、強制中止、最後一列破損時能恢復。
- 單按、雙按、按住、放開、debounce、取消及斷線重連不重複建立標記。
- 人工標記的前後回看區間、GPS 配置及自動事件重疊計算正確。

### 實機測試

- 靜置 10 分鐘：基線、漂移、熱、電量與容量。
- 三軸定向敲擊：確認 x／y／z 及 UI 標籤。
- 手機旋轉與拿起：確認品質事件而非只產生紅色熱點。
- 30、60、120 分鐘前景記錄：確認掉樣率、UI 流暢與檔案完整。
- GPS 良好、精度降低、隧道／室內中斷：確認灰色區及不偽造位置。
- 同條件同路段至少 3 趟：檢查橘／紅事件的重現位置。
- 以 phyphox 或 SensorLog 做獨立對照趟：比較數值量級與主要頻率趨勢。
- 至少以一款 Game Controller profile 裝置和一款指定 BLE 按鍵完成按鍵延遲、連續 100 次按鍵、斷線及一小時連線測試；只公布實際通過的相容型號。

## 15. 後續鐵路圖資、里程與巡查資訊

此模組規劃於 V0.1.0 之後導入。V0.0.1 先確保 GPS、Motion、速度與精度來源資料可靠，後續再加入合法授權且具有版本資訊的鐵路線形圖資。

### 圖資與里程欄位

| 欄位 | 用途 |
|---|---|
| `routeID`、`routeName` | 唯一識別鐵路路線 |
| `trackID`、`direction` | 區分上下行線、平行股道與里程增減方向 |
| `geometry` | WGS 84 軌道中心線 polyline |
| `chainageStart_m`、`chainageEnd_m` | 線段對應的正式或圖資推估里程 |
| `stationingEquation` | 處理斷鏈、重複里程及里程修正 |
| `source`、`license`、`sourceVersion` | 保存圖資來源、授權、版本及更新日期 |
| `declaredAccuracy_m` | 圖資本身的精度；未知時不得自行填入 |

一般地圖即使畫有鐵路線，也不一定包含可靠股道、正式里程或工程精度，不能直接當作軌道里程真值。

### GPS 貼線與里程換算

1. 將有效 GPS 點投影到鄰近鐵路線，建立多個候選線段。
2. 以 GPS 精度、點到線距離、行進方向、速度連續性及前後候選關係評分。
3. 在平行股道、折返站及路線交會處避免任意跳線；無法判定時保留多個候選。
4. 以選定線段的累積距離加投影距離換算 chainage，再套用正式斷鏈資料。
5. 分別換算熱點開始、中心與結束時間，輸出起訖里程範圍而不是單一點。
6. 隧道或 GPS 長缺口證據不足時，標示「無法定位」，不可硬接到最近軌道。

### 疑似振動熱點地段

未經專業軌檢資料確認前，畫面與輸出一律稱為「疑似振動熱點地段」，不直接命名為軌道不整。每段規劃保存：

```text
routeID, trackID, direction
chainageStart_m, chainageCenter_m, chainageEnd_m
chainageReference, chainageConfidence
gpsHorizontalAccuracyMedian_m, gpsHorizontalAccuracyP95_m
mapMatchResidualMedian_m, alongTrackUncertainty_m, crossTrackUncertainty_m
speedMean_m_s, speedMin_m_s, speedMax_m_s, speedP95_m_s
speedAccuracyMedian_m_s, validSpeedRatio
motionScore, perceivedMarkerCount, repeatPassCount
mapSource, mapVersion, analysisVersion
```

### 巡查速度

- App 記錄列車當時的實際速度與 `speedAccuracy`，不是命令列車以某速度行駛。
- 每個疑似地段顯示平均、最低、最高、P95 速度及有效速度比例。
- 同一路段跨趟比較時先依速度帶分組，例如每 10 km/h 一帶；速度差異太大時不直接比較。
- 停站、加速與減速區段獨立標記，避免和穩定巡航資料共用基線。
- 若未來有專用巡查模式，目標速度由鐵路營運或工程單位制定，App 不提供行車速度指令。

### 定位與里程精確度

| 指標 | 意義 |
|---|---|
| GPS horizontal accuracy | Core Location 回報的平面不確定半徑 |
| Map-match residual | GPS 點至選定軌道中心線的距離 |
| Along-track uncertainty | 沿軌道方向可能前後偏移的範圍 |
| 圖資精度與版本 | 軌道中心線是否足以作里程定位 |
| 候選唯一性 | 附近是否存在平行股道或交會路線 |
| GPS gap | 事件是否位於長時間無定位區段 |
| 重複通過一致性 | 多趟熱點換算後的里程是否集中 |

畫面分成高、中、低及無法定位四級。精度較差時放大起訖里程範圍並使用灰色虛線；不得以座標小數位數或最近軌道距離冒充真實定位精度。

### 圖面整合

- 地圖可切換「GPS 軌跡」與「鐵路里程」模式。
- 鐵路模式顯示路線、股道／方向、公里標及疑似地段起訖里程。
- 疑似地段沿軌道以色帶呈現，帶狀邊界包含里程不確定範圍。
- 點選地段顯示速度統計、GPS P95 精度、貼線殘差、里程可信度、通過次數及人工感受標記數。
- 多趟結果區分「單趟觀察」與「重複出現」；只有條件相近且位置範圍重疊才提高可信度。

### 驗證方式

- 使用具有已知正式里程的測試點或里程標驗證 chainage 偏差。
- 分別測試單線、複線、平行多股道、路線交會、車站與隧道。
- 比較 GPS reported accuracy、實際位置誤差與 map-match residual。
- 同一路段、方向、車型、固定方式與相近速度至少重複 3 趟。
- 取得合法專業軌檢資料時，只在時間與里程基準一致後進行盲比對。
